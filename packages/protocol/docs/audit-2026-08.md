# Security review — circuits and contracts


> **Point-in-time record, 2026-08.** Kept as written; the code has moved since. Changes that
> post-date this pass and that it therefore does not cover: note keys now come from a BIP-39
> recovery phrase rather than a `personal_sign` signature; an alias is owned by a secp256k1
> key derived from that phrase rather than by the registering wallet, so `msg.sender`
> authorises no owner action at all; and signature verification, deadline and nonce bump are
> unified in `_consumeAuthorization`. See
> [keys-and-authorization.md](keys-and-authorization.md) for the current design.

Manual review of `transact.circom`, `merkleProof.circom`, `HaliasPool`, `HaliasRegistry`,
`HaliasController`, `SMTRegistry`, `MerkleTreeWithHistory`, `TransactVerifier`. 2026-08-10.

Reviewed by the same party that wrote the code, which is a real limitation — the findings
below came from checking against known failure patterns in audited prior art (Tornado Nova,
Semaphore, World ID) rather than from re-reading my own reasoning, because re-reading your
own reasoning reproduces your own blind spots. Two earlier bugs (registry roots born

**circomspect 0.9.0 (Trail of Bits) was run** — see "Automated analysis" below. Slither and

## Verified sound

Each of these is a specific way this design could have been broken, checked and found
closed.

**Public-signal malleability → double spend.** The single most dangerous failure available
to this architecture. If the verifier did not bound public signals to the scalar field, then
for a nullifier `N`, the value `N + r` reduces to the same field element: the proof verifies
identically while `spentNullifiers[N]` and `spentNullifiers[N + r]` are different storage
slots, and every note is spendable twice. `TransactVerifier.verifyProof` calls `checkField`
on all nine signals (lines 198–214) and returns false above `r`. Closed.

**Unconstrained public input.** A public signal appearing in no constraint has no effect on
the proof, so a submitter can substitute any value for it. `paramsHash` is anchored by
`signal paramsHashSquare <== paramsHash * paramsHash` (transact.circom:382) — the same
device Tornado Nova uses for `extDataHash`.

**Non-binary path indices.** `merkleProof.circom:19` constrains
`pathIndices[i] * (1 - pathIndices[i]) === 0`. Without it a prover picks arbitrary field
elements for the mux selector and forges membership. `NoteNullifier` used to pack the same signals with
`Bits2Num`, which does *not* bound its inputs, and was safe only because `MerkleProof` is
instantiated unconditionally beside it. That coupling was load-bearing and invisible; the
constraint now sits inside `NoteNullifier` as well — see A1.

**Conservation wraparound.** `sumIns + publicAmount === sumOuts` over a 254-bit field.
Amounts are `Num2Bits(248)` and `publicAmount` is bounded to `[-2^248, 2^248)`, so the
largest reachable intermediate is under `2^250` — three orders of magnitude below `p`. No
wrap.

**Nullifier soundness.** `Poseidon(nullifierKey, leafIndex, NULLIFIER_DOMAIN)` does not bind
the commitment, unlike Tornado Nova. It is still sound: the Merkle proof binds `leafIndex` to
one commitment under a given root, and that commitment contains `Poseidon(nullifierKey, 1)`,
so spending requires the key the note names. The 3-arity domain separator makes collision
with the 2-arity `nullifierKeyHash` impossible, so a spend never publishes a value linkable
to the registry.

**Dummy-input forgery.** Zero-amount inputs skip the Merkle check, so a prover chooses their
key and index freely and could publish any nullifier they can compute. Reaching a victim's
nullifier requires a Poseidon preimage. Not reachable.

**Slot zero.** `aliasSlot` is stored offset by one (`slot = ++nextAliasSlot`, `pathKey =
slot - 1`), so the first registration holds slot 1 and `aliasSlot[h] != 0` is a valid
existence test. Had slots started at zero, the first alias registered would read as
unregistered and be re-registrable by anyone.

**Field bounds on every leaf input.** Poseidon reduces silently, so `p + 5` and `5` commit
the same leaf — two records sharing a leaf, or a stored value differing from the committed
one. `_checkKeys` bounds `spendingPubkey` and `nullifierKeyHash`; `setDataHash` bounds
`dataHash` separately, which is required because registration writes a zero `dataHash` and
never passes through `_checkKeys` for it.

**Alias-hash injectivity.** The SMT keys on `aliasHash % FIELD_PRIME`, which is lossy.
`aliasByKey` enforces one alias per reduced key, so "one alias, one key" is an invariant of
the contract rather than an assumption of everything built on it.

**Registry root freshness.** `registryRootBlock[smtRoot] = block.number` stamps the
*outgoing* root at supersession. Stamping the incoming root at creation makes a root on a
quiet registry expire before it is superseded — born already stale. Matches World ID's
`requireValidRoot`.

**ERC-721 escape hatch.** Alias keys must move with ownership, or the previous owner keeps
decrypting. `transferFrom`, the 4-arg `safeTransferFrom`, `approve` and `setApprovalForAll`
all revert. The 3-arg `safeTransferFrom` is **not** overridden and cannot be: OZ 5.6.1
declares it non-virtual, so Solidity rejects an override outright. It is closed only because
that non-virtual implementation routes through the 4-arg overload — a property of the
dependency rather than of this code, which an OZ change could silently reverse. Pinned by
test (`disables plain ERC-721 transfer and approval` exercises the 3-arg form explicitly), so
a version bump that reopened it would fail rather than ship.

**Fee-measurement spoofing on claim.** `claim` measures `address(this).balance` before and
after `pool.transact` instead of recomputing the expected payout. A relayer paid mid-call
could otherwise forward ETH to fake `received`. `receive()` reverts unless
`msg.sender == pool`, so the only ETH that can land during the window is the pool's.

**Reentrancy.** Pool and domain both `nonReentrant`, and the pool follows CEI independently —
nullifiers spent and commitments inserted before any transfer. A malicious payee re-entering
`transact` or `claim` is blocked twice over.

## Findings

### F1 — A prepared claim is invalidated by any concurrent registration (medium, liveness) — FIXED

**Was confirmed by test**, not inferred.

`claim` is the only operation that proves against a registry root **that does not exist
yet**. The domain registers the claimer *then* calls the pool, because the claimer's change
note is a non-zero output and the circuit demands registry membership for those — against a
root that already includes them. So the client predicts both the post-registration root and
its own slot:

```ts
const ownSlot = Number(await this.registry.nextAliasSlot());
postSmt.update(ownSlot, smtKey, leaf);   // proves against postSmt.root
```

Any registration landing in between shifts `nextAliasSlot` and changes the tree, so the
predicted root is never current and the pool rejects with `RegistryRootNotCurrent`.

Ordinary transfers and withdrawals are immune: they prove against a root that already
exists, and `REGISTRY_ROOT_MAX_AGE` (7200 blocks) absorbs concurrent registrations. Claim
has no such window because its root is in the future.

Reproduced in `e2e-live.ts`: prepare a claim, register one unrelated alias, re-simulate —
the claim reverts. No funds are at risk and the invite is not consumed; the claimer retries.
But this is the onboarding path, and on a busy registry a claimer can be starved
indefinitely by ordinary traffic with no backoff, no queue and no error that explains why.
A relayed claim is worse: the prepared blob is dead on arrival and the claimer is not present
to rebuild it.

**An attempted structural fix was unsound and was reverted.** The idea was to address the
change note to the *invite* account, which already exists — no future root to predict, F1
gone, and SDK-only. It fails for two reasons the test suite caught immediately:

- The change note becomes indistinguishable from the invite note it came from, so
  `findInviteNote` locates it and the invite reads as unspent. It can be claimed again.
- The **inviter knows the secret**. Routing the remainder under those keys hands them the
  ability to spend the claimer's change or buy another name with it. Today the change sits
  under the claimer's own keys, which the inviter cannot touch.

The second is the disqualifying one: it converts a liveness bug into a custody bug. The
prediction stays, and the comment in `claimInvite` now records why, so the idea is not
re-attempted.

**Fixed in the circuit.** The proof now carries the insertion: it proves against a root that
already exists, shows the target slot is empty there, and derives the tree that results from
adding the claimer's leaf. Nothing is predicted, so nothing another party does can invalidate
it. `pendingLeaf` is a tenth public signal supplied by the contract — never by the prover —
and the pool requires it to equal what the registry armed in transient storage, which is zero
on every path but a claim.

Two things about the implementation are worth carrying forward, because the design as first
written in `f1-claim-root-prediction.md` had a hole:

- **The pending siblings must be proved against `registryRoot` before being reused.** Deriving
  the post-insertion root from unconstrained siblings lets a prover fabricate *any* tree
  whenever `pendingLeaf` is non-zero — which makes registry membership vacuous on exactly the
  path that mints new aliases. Proving the slot currently holds the empty leaf ties them to
  the real tree, and has a second effect worth having: an insertion can only land on a free
  slot, so it can never overwrite an existing alias.
- **The cost estimate was wrong by an order of magnitude.** The doc predicted ~+2,500
  constraints. It is **77,790 → 111,112, +33,322 (+43%)**, because the fix needs two 32-level
  Merkle computations rather than one, and a 32-level Poseidon proof is ~16,000 constraints
  here, not 2,500. Still inside the 2^17 ceremony domain (131,072), so no ptau upgrade — but
  the headroom went from 53k to 20k, and the next circuit change should check that first.

Regression coverage: a prepared claim survives a registration, an `updateAliasData` and a
full offer/accept landing in between; an ordinary `transact` claiming an insertion is
rejected; a claim carrying an insertion other than the one being registered is rejected; the
arming does not survive into a later transaction; only the controller may arm.

Severity note: a griefer can pre-commit throwaway names and reveal one on demand to invalidate
a claim in flight, for the price of a registration fee. So this is not only accidental
contention.

### F5 — Registration is front-runnable; there is no commit-reveal (high)

**Confirmed by test.**

`register(bytes32 aliasHash, ...)` carries the alias hash in plain calldata and the domain
has no commitment scheme. Whoever lands first owns the name. That is the classic ENS
front-running problem, and ENS solved it with commit-reveal for exactly this reason.

The harm is worse than squatting. A front-runner registers the contested hash with **their
own keys**, so the registry now answers a lookup of that name with the attacker's
`spendingPubkey` and `encryptionPubkey`. Everyone who later pays the name pays the attacker,
in notes only the attacker can decrypt. The victim gets a reverted transaction and no
indication of what happened.

Reproduced end to end in `e2e-live.ts`: a squatter registers the target name, the victim's
registration reverts with `AliasTaken`, `lookup()` returns the squatter's spending pubkey,
and the squatter holds the NFT.

`registrationFee` is not a defence — the attacker pays the same fee and can resell or ransom
a name worth more than it. Nor is the plaintext staying private: the hash alone is enough,
since the attacker registers the *hash*, and publishing a name is optional anyway.

This interacts badly with the positioning. The whole premise is an alias you can verify
rather than a hex string you cannot; a name service where the name you typed can be taken
mid-transaction undermines that more than an equivalent bug would elsewhere. Address
poisoning was supposed to be the attack this design eliminates.

**Fixed.** Two-phase commit-reveal, contract-only — no circuit change, no ceremony.

Surface added: **one external method** (`commit`), one view helper
(`registrationCommitment`), a mapping, two constants, and one parameter on `register`.

`msg.sender` is bound into the commitment, and that part is not decoration. `_record` makes
`msg.sender` the owner, so without it a front-runner could copy the *reveal* verbatim and
mint the alias to themselves while the victim kept the keys. Binding the sender makes a
copied reveal hash to a commitment that does not exist.

`MIN_COMMIT_AGE` is one block, which is the whole requirement: someone who first learns the
name from the reveal cannot commit and reveal in the same block. `MAX_COMMIT_AGE` is 7200 so
abandoned commitments cannot be hoarded and used much later.

{claim} deliberately keeps a single transaction. Its owner is already fixed inside the proof
through `externalData`, so a copied claim registers to the bound owner rather than the
copier — blockable, but not stealable, and the claimer by definition may have no ETH to spend
on a second transaction.

### F6 — Concurrent spends and duplicate registrations are safe (no action)

Checked while investigating F5, and recorded so it is not re-derived.

Double-spending the same note across two transactions cannot succeed: the nullifier check and
its write are in one transaction and the EVM is serial, so the second reverts with
`NullifierAlreadySpent`. Registering the same alias twice reverts with `AliasTaken`. Both
asserted in `e2e-live.ts`.

Exact-copy replay — resubmitting someone's proof and params verbatim with higher gas — remains
possible and remains pure griefing: every destination is committed in `paramsHash`, so the
copier pays gas and redirects nothing. Already noted in the circuit.

### F7 — `updateKeys` could not rotate the key that matters (medium) — FIXED

An alias holds three keys; `updateKeys` wrote two of them and never `spendingPubkey`. So the
one compromise that loses funds was the one the control named for it could not address.

**Fixed by removal**, not by extension. `reassign` already replaces all three in place, so
rotation is a handover to yourself — offer the alias to your own address, accept with keys
from a fresh derivation index. Strictly more capable than what was deleted, and since both
halves carry signatures the whole rotation is relayable, which is the case that matters:
re-keying after a compromise is exactly when you may be unable to pay for a transaction.

Removing it also deleted a registry leaf writer, shrinking F1's surface from four paths to
three. Cost: a rotation now clears `dataHash`, which is zero on every alias in existence.
Detail in `key-rotation-and-transfer.md`.

### F8 — A handover misdirects payments for one window afterwards (medium, funds)

Note commitments bind `spendingPubkey` at creation, and the pool accepts any registry root
superseded within `REGISTRY_ROOT_MAX_AGE`. So for one window after an alias changes hands, a
sender proving against a stale-but-still-valid root pays **the previous owner's keys** while
their client reports the payment as sent to the new one. Those notes are not recoverable by
the buyer; they are ordinary notes under the seller's key.

`key-rotation-and-transfer.md` analysed this window and called it a confidentiality exposure.
That is right for a self-rotation, where you keep the old keys. For a transfer between two
parties it is fund misdirection, because the old keys belong to somebody else. Same
mechanism, different severity, and the distinction was not drawn.

The realistic trigger is not malice but staleness: a relay blob prepared before the handover
and submitted after. An ordinary interactive send is exposed only for the seconds between
proving and inclusion, since the client proves against the current root.

**Mitigated, not closed.** `REGISTRY_ROOT_MAX_AGE` went from 7200 blocks to `1 hours`, which
cuts the window from about a day. Two changes, and the units mattered as much as the number:
the property being bounded is time, and 7200 blocks is a day on mainnet but four hours on a
two-second L2 — the guarantee would have silently changed meaning with the deployment target.

What remains open is the last hour. It is not fixable in the pool, which cannot know an alias
changed hands, and shrinking the window further trades against the liveness it exists for.
The precise fix is client-side: refuse to submit a payment whose registry root predates an
`AliasReassigned` for that recipient, and expire relay blobs on the same condition.

### F2 — Admin fee changes stall in-flight claims (low)

`claim` reverts unless `received == registrationFee` exactly. The payout is fixed inside the
proof, so changing `registrationFee` between proof generation and inclusion invalidates every
outstanding claim. Same class as F1 but admin-triggered rather than traffic-triggered.
Acceptable — the admin is already trusted for fees, and no funds are at risk — but it means
a fee change is a disruptive operation and should be rare and announced, not routine.

### F3 — ETH has no per-note ledger (informational, already documented)

`_debitPool` checks `poolTokenBalance[token]` for ERC-20 but only `address(this).balance`
for ETH. If the circuit's conservation constraint were ever broken, an ETH over-withdrawal
would be caught only once it exceeded the entire pool, whereas the same bug against a token
is caught at that token's outstanding notes. Documented in-code as a deliberate trade
(one SSTORE per ETH transact). Fair, and worth revisiting if a ledger ever becomes cheap.

### F4 — Pool root history is unbounded (informational)

`knownPoolRoots` is a permanent mapping; Tornado uses a 30-root ring buffer. This differs in
the safe direction — an old proof never expires, so no user loses a note to slow proving —
and costs one SSTORE per transact. No action, but it is a deliberate divergence from the
prior art and should not be mistaken for an oversight.

## Automated analysis — circomspect 0.9.0

Re-run against the finalised circuits, after the A1 fix and the F1 change:

```
circomspect circuits/transact.circom -L ../../node_modules/circomlib/circuits -L circuits/lib
  → 4 issues found
circomspect circuits/lib/merkleProof.circom
  → No issues found
```

All four are patterns this design already reasons about, and none is exploitable as written.
A2, A3 and A4 are unambiguous false positives on aliasing grounds — every flagged conversion
is 32 or 248 bits wide, far below the prime, so no input has two representations. A1 was
flagged for aliasing that cannot occur, but pointed at a real missing input bound underneath;
that is now fixed and the warning that remains is about the template, not the constraint.

### A1 — `Bits2Num` in `NoteNullifier` (transact.circom:79) — worth acting on

Circomspect flags aliasing. That part is a false positive: `levels = 32`, so the packed value
is under `2^32` and every bit pattern maps to a distinct field element. Aliasing needs an
input at least the size of the prime.

The real issue is the one underneath it. `Bits2Num` does **not** constrain its inputs to be
binary. If `pathIndices` were free field elements, a prover could pack the same note's path
into a different `leafIndex`, produce a different nullifier for a note already spent, and
spend it twice.

That is closed today only because `MerkleProof` — a *different* template — constrains
`pathIndices[i] * (1 - pathIndices[i]) === 0` on the same signals, and is instantiated
unconditionally for every input including zero-amount dummies. The nullifier's soundness
therefore depends on a sibling component continuing to be instantiated, unconditionally,
forever. Move the merkle proof inside a conditional, or reuse `NoteNullifier` anywhere else,
and it silently becomes a double-spend.

**Fixed.** `pathIndices[i] * (1 - pathIndices[i]) === 0` now sits inside `NoteNullifier`, so
the component is sound on its own terms rather than by coincidence of its neighbours.

Cost was exactly as predicted: **77,726 → 77,790 constraints, +64** (2 inputs x 32 levels,
0.08%). Recompiled, `--dev` ceremony re-run, verifier re-exported.

The regenerated `TransactVerifier.sol` came out **byte-identical**, which looked wrong and is
not. Both circuits pad to the same 2^17 QAP domain, and the added constraints involve only
private signals — so the public-input polynomials, and therefore every `IC` point, are
unchanged. `alpha`/`beta`/`gamma`/`delta` come from the ptau plus fixed `--dev` entropy.
Confirmed rather than assumed: the vkey's `IC0`, `IC8` and `delta` were compared against the
Solidity constants and match, and 131 Hardhat tests generating real proofs verify against it.

circomspect still reports the `Bits2Num` warning, because it flags the template instantiation
rather than whether the inputs are bound. The aliasing it names cannot occur at `levels = 32`;
the missing bound it did not name is now closed.

### A4 — `Num2Bits(32)` on `pendingSlot` (transact.circom:299) — false positive

New with the F1 fix, and the same shape as A3. `registryLevels = 32`, so a value at or above
`2^32` has no satisfying decomposition and anything below it has exactly one; aliasing needs
an input at least the size of the prime.

The prover does choose `pendingSlot` freely, which is worth stating separately from the
aliasing question. It is bounded by the emptiness proof: the slot must hold the empty leaf
under `registryRoot`, so an insertion can only land somewhere genuinely free. Choosing a
*different* free slot than the registry actually assigned is harmless — the slot appears
nowhere in a note commitment, the derived tree is never persisted on chain, and the change
note stays spendable later against the real tree at its real position.

### A2 — `paramsHashSquare` single-use (transact.circom:382) — false positive

The heuristic flags intermediate signals appearing in only one constraint as possibly
under-constrained. Here that is the entire purpose: the signal exists to force `paramsHash`
into the R1CS, because a public input in no constraint can be freely substituted. Same
device as Tornado Nova's `extDataHash`. Removing it would be the bug.

### A3 — `Num2Bits(32)` on `outRegistryIndex` (transact.circom:303) — false positive

Same aliasing check as A1. `registryLevels = 32`, so a value at or above `2^32` has no
satisfying decomposition and anything below it has exactly one. `Num2Bits_strict` would add
constraints to rule out an aliasing that 32 bits cannot express. Already argued in-circuit at
lines 300–302.

## Not covered

- **Trusted setup.** Still a single self-generated `--dev` ceremony. No amount of circuit
  review substitutes; a multi-party ceremony is a prerequisite for real funds and is tracked
  separately.
- **Solidity static analysis.** Slither and Aderyn have not been run; the Solidity review
  here is manual. (circomspect *was* run — see "Automated analysis" above.)
- **Economic and MEV analysis.** Exact-copy proof replay is documented in-circuit as
  griefing (victim's transaction reverts on a spent nullifier); no broader mempool analysis
  was done.
- **The verifier contract itself** is snarkjs-generated and was checked only for public-input
  bounds, not audited line by line.
